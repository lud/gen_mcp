# OAuth scopes and authorization helpers

## Goal

Let a gen_mcp server act as an OAuth 2.1 resource server, as the MCP
authorization spec describes it, without gen_mcp becoming an authorization
server or owning token verification. gen_mcp ships three things:

1. A helper that answers a 401 with the `WWW-Authenticate` challenge MCP
   clients need to start the OAuth flow.
2. Scope enforcement in `GenMCP.Suite`: components declare the scopes they
   require, the Suite compares them with the scopes the request's token was
   granted, and refuses with a 403 `insufficient_scope` challenge so the
   client can step up.
3. A guide tying it together.

## Context

The MCP authorization spec (2026-07-28, also 2025-11-25) makes the server a
resource server. The parts that concern us:

- An unauthenticated request gets a 401 whose `WWW-Authenticate: Bearer`
  header carries `resource_metadata`, the URL of the RFC 9728 protected
  resource metadata document, and SHOULD carry `scope`.
- A valid token whose scopes are too narrow gets a 403 with
  `error="insufficient_scope"`, `scope` listing **all** scopes the operation
  requires (in one challenge, not incrementally), and `resource_metadata`.
- "Servers MUST account for scope hierarchies, where a broader scope implies
  narrower ones."

The `sake` library (hattoriai/sake) embeds a full authorization server. We
deliberately stay on the resource-server side: authorization servers are the
job of Keycloak, Auth0, Boruta, ExOauth2Provider and the like.

## Design

### Token verification stays in user code

The user verifies the token in their own plug, in the router pipeline in
front of the MCP transport. It puts the identity and the granted scopes in
conn assigns, which reach `channel.meta` through `:copy_assigns`, as today.
gen_mcp ships no token-checking plug.

### 401 helper

`GenMCP.Auth` exposes a function for that plug to refuse a request: it sends
a 401 with `WWW-Authenticate: Bearer resource_metadata="…"` and halts the
conn. Options:

- `:resource_metadata` — the metadata URL. Defaults to the RFC 9728 §3.1
  derivation from the request: origin, then
  `/.well-known/oauth-protected-resource`, then `conn.request_path`. The
  override exists for proxies, where the conn's origin is not the one clients
  reach.
- `:scopes` — optional, rendered as the `scope` parameter.
- `:error` / `:error_description` — optional (RFC 6750 `invalid_token` for an
  expired or invalid token).

Parameter values are rendered as RFC 9110 quoted strings. The derivation of
the metadata URL is a public function of its own, shared with the 403 below.

### Required scopes

`GenMCP.Suite.Tool`, `GenMCP.Suite.ResourceRepo` and
`GenMCP.Suite.PromptRepo` all get the same optional callback:

```elixir
@callback required_scopes(arg) :: [String.t()]
```

The same name on all three is deliberate: this is security, and the
declarations must read the same everywhere. Undefined means no requirement.
A return value that is not a list of strings raises
`GenMCP.CallbackReturnError`. The scopes are all required (AND); a scope
granted through a hierarchy is the comparator's business, below.

A repo's scopes apply to the whole repo: the library answers "may this token
access notes", the repo's own code answers "may Alice read Bob's note".

The `use` macros generate the callback from a `required_scopes:` option.
Giving both the option and a `def required_scopes/1` raises at compile time,
as `input_schema`, `output_schema` and `cache_control` already do on
`GenMCP.Suite.Tool` (`check_opts_def_conflicts`). It is not an `info/2` key,
because an `info/2` clause silently wins over its option, and access control
must not be overridden silently.

`ResourceRepo` and `PromptRepo` have no `__using__` today. They get one,
supporting `:prefix` and `:required_scopes`.

### Suite options

- `granted_scopes` — a function of arity 1 receiving the channel, returning
  the list of scopes the request's token was granted (typically read from
  `channel.meta`). **Setting this option is the opt-in**: without it, nothing
  is checked and listings are untouched, whatever the components declare.
  With it, every check below runs, even when it returns `[]`.
- `scope_check` — a function of arity 2, `(required, granted) -> boolean`,
  both lists. Defaults to `&GenMCP.Auth.scopes_granted?/2`.

When `granted_scopes` does not return a list, or `scope_check` does not
return a boolean, the request fails with an internal error and the operation
never runs (fail closed). Both are runtime errors from user functions, so a
single rescue around the check covers them.

### Comparators

- `GenMCP.Auth.scopes_granted?(required, granted)` — exact string match:
  every required scope is in `granted` (`required -- granted == []`, with
  duplicates in `required` not causing a false refusal).
- `GenMCP.Auth.scopes_prefix_granted?(required, granted)` — opt-in, never
  the default. A required scope is granted when a granted scope equals it or
  is a prefix of it on whole segments separated by `:`. With
  `["repo", "foo:bar"]` granted, `"repo:read"` and `"foo:bar:baz"` are
  granted; `"repository"` and `"foo:barbaz"` are not.
- `GenMCP.Auth.scopes_prefix_granted?(required, granted, separator)` — the
  same with another separator, for users who wrap it in their own `/2`
  function (an option takes a `&Mod.fun/2` capture, so the separator cannot
  be passed there).

Hierarchies of another shape (GitHub's verb-first `admin:org` implying
`write:org`) are a custom `scope_check`.

### What is checked, what is listed

With `granted_scopes` set:

| Method | Behaviour when scopes are missing |
| --- | --- |
| `tools/list` | Tool still listed (the client must see it to step up). |
| `tools/call` | 403 `insufficient_scope`. |
| `resources/templates/list` | Template still listed. |
| `resources/list` | The repo is skipped, no error. |
| `resources/read` | 403 `insufficient_scope`. |
| `prompts/list` | The repo is skipped, no error. |
| `prompts/get` | 403 `insufficient_scope`. |

The check runs after the component is resolved: an unknown tool, resource
or prompt keeps its current error. Hiding a component entirely, by
permission rather than by token scope, is done with a `GenMCP.Suite.Extension`
reading the channel, and needs nothing from this spec.

**Skipping in listings.** The skip happens inside the list function given to
`paginate_repos`, which returns `{[], nil, cache_control}` for a denied repo.
`paginate_repos` already moves to the next repo on an empty page, and the
repo indices encoded in the cursor stay stable.

**Cache hints.** With `granted_scopes` set, `resources/list` and
`prompts/list` answer with a private cache hint, whatever the repos declare:
the same listing differs between tokens.

### The 403 response

The Suite returns a new error reason carrying the required scopes (all of
them, not only the missing ones). `GenMCP.Error.cast_error/1` maps it to HTTP
403 and a JSON-RPC error whose `data` lists the required scopes. The
`WWW-Authenticate` header (`Bearer error="insufficient_scope", scope="…",
resource_metadata="…"`) is added where the response is written:
`GenMCP.Transport.Relay` (its private `write_error`) is shared by both
transports, but
`cast_error/1` and the codecs' `render_error/3` only carry a status and a
payload today, so either `Relay` adds the header for that reason or the
render contract grows headers. The check runs before dispatch, so the
response is never already streaming.

The transport accepts the same `:resource_metadata` override as the 401
helper, and otherwise derives the URL from the conn the same way.

### Guide

A new guide in `guides/` covers:

- verifying tokens in a plug of one's own, and refusing with the 401 helper;
- serving the protected resource metadata document (static JSON written by
  the user);
- passing identity and scopes with `:copy_assigns`;
- `required_scopes`, `granted_scopes`, `scope_check` and the comparators;
- hiding components by permission with an extension;
- pointing at an authorization server (external providers, Boruta,
  ExOauth2Provider).

## Out of scope

- An authorization server, token verification, JWT/JWKS handling.
- A plug or helper serving the protected resource metadata document.
- Scopes computed from request arguments (the spec allows it). A component
  needing that would return the 403 reason itself; not designed here.
- Subscription handlers: they receive the channel and check what they need.
- Step-up for authentication strength (RFC 9470 `acr_values`, `max_age`).

## Open questions

- **RPC code of the 403 body.** No MCP code exists for it. The origin 403
  uses `-32600` (invalid request); reuse it unless a better fit appears.
- **Declared scopes without `granted_scopes`.** A component declaring
  `required_scopes` on a Suite that never set the option runs unchecked.
  Components come from channel-dependent extensions, so this cannot be
  caught at init. A one-time runtime warning is an option.
- **`cache_control:` in the repo `__using__`.** Repos already have the
  optional `cache_control/1` callback; the `use` option would match `Tool`.

## Acceptance criteria

- The 401 helper sends the challenge with the derived or overridden
  `resource_metadata`, the optional `scope` and error fields, and halts.
- `required_scopes/1` works the same on tools, resource repos and prompt
  repos, from the `use` option or a `def`; both at once fails compilation; an
  invalid return raises `GenMCP.CallbackReturnError`.
- Without `granted_scopes`, behaviour and cache hints are unchanged.
- With it, the table above holds on the 2026 transport and on the 2025
  compat transport, and the 403 carries the full challenge.
- `resources/list` and `prompts/list` skip denied repos across pages without
  corrupting cursors, and their cache hint is private.
- `scopes_granted?/2` and `scopes_prefix_granted?/2,3` behave as described,
  including segment boundaries.
- A non-list from `granted_scopes` or a non-boolean from `scope_check` fails
  the request with an internal error, and the component is not called.
- The guide exists and follows the guide content rules.
