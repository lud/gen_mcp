# Surface server start errors instead of a bare internal error

A transport mounted with options that do not validate answers every request
with an opaque `500`, and by default says nothing anywhere else. Found while
researching whether `plug_init_mode` could catch such mounts at compile time
(it cannot — see feature 021).

## The failure today

`GenMCP.Suite.init/1` returns `{:stop, %NimbleOptions.ValidationError{}}`, the
worker fails to start, and `GenMCP.Error.cast_error/1` maps the struct to a
generic internal error. A mount missing `:server_name` produces, on every
request:

    status: 500
    {"error": {"code": -32603, "message": "Internal Error"}, "id": 1, ...}

Which is indistinguishable from a handler crashing mid-request. The real
message — `required :server_name option not found` — reaches only the
`[:gen_mcp, :server, :start_error]` telemetry event, and
`GenMCP.TelemetryLogger` is **opt-in**.

`GenMCP.Application` attaches it when `Mix.env() != :prod`, which never fires
for a consuming application: Mix compiles dependencies with the `:env` dep
option, and that defaults to `:prod` whatever environment the parent runs in.
So the attach happens for gen_mcp's own tests and never for a library user,
who gets nothing at all unless they called `GenMCP.attach_default_logger/1`
themselves.

So the one failure guaranteed to affect 100% of requests was the one with no
diagnosis attached.

## The fix

`GenMCP.Server.start_worker/2` logs the reason itself, next to the telemetry
event it already emitted. Two clauses: an option validation failure gets the
`Exception.message/1` plus a line saying to look at the mount, since that is
what carries the options; anything else is inspected as-is.

The client response is unchanged — the reason is for the operator, not the
client, and a JSON-RPC error body is not the place for server configuration
detail.

### Why not conditional on the logger being attached

Checking `:telemetry.list_handlers/1` before logging would avoid a duplicate
line for applications that did attach `GenMCP.TelemetryLogger`, but it reports
handlers, not whether any of them logs — an application with its own metrics
handler on that event would silence the diagnosis. A server that cannot start
is always worth saying out loud, so the log is unconditional and the duplicate
line is accepted.

This is the only `Logger` call in `lib/` outside `GenMCP.TelemetryLogger`,
which is deliberate: everything else in the library is a per-request event
where opt-in telemetry is the right channel, whereas this one is a permanent
misconfiguration.

## Acceptance — done

* A mount missing `:server_name` logs a message naming the option and pointing
  at the mount. Verified to fail before the change (the telemetry logger alone
  did not satisfy it) and pass after.
* A non-validation `{:stop, reason}` logs the reason as-is.
* The client response and every existing behaviour are unchanged: 431 tests
  green.

## Not included

Making the mount fail at compile time — that needs a macro, and is feature 021.
