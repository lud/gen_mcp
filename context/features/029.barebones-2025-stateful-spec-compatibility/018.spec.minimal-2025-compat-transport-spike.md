# Minimal 2025 compat transport spike

First slice of feature 017. Goal: prove the **translation-at-the-boundary**
design end to end with the least code, so we learn whether a 2025 client can be
served by the stateless core without the Suite, the providers, or the worker
contract knowing anything about 2025.

Explicitly a spike: throwaway-able if the design does not hold.

## What this slice does not do

No `GenMCP.MCP.V2511` entity regeneration and no `V2511` validator. The 2025
request surface is hand-written in the compat plug and translated straight into
existing `V2607` structs. `tools/list` and `tools/call` are the two methods
whose 2025 and 2026 shapes are close enough that translation is small, which is
exactly what makes them the right probe. Codegen can land later as a drop-in
replacement for the hand-written validation, once we know the boundary works.

## Validation without a 2025 vocabulary

With no `V2511` schemas there is no validator, so validation splits three ways:

1. **The JSON-RPC envelope** is checked by hand, once, in `normalize/1` before
   any routing: `id` must be a scalar, `params` must be an object, `_meta` is
   coerced to a map. Past that point the translation reads fields without
   guarding every access. These rejections stand in for what
   `GenMCP.Validator` does on the 2026 side, so they answer the same way: a
   pre-dispatch `400`, not the `200` that `{:invalid_params, _}` carries for an
   application-level failure after dispatch.
2. **The per-method fields this shim reads** — `tools/call`'s `name` and
   `arguments`, `tools/list`'s `cursor` — are guard-checked in `Translate`.
3. **Tool arguments**, the part that actually matters, are validated
   downstream by `GenMCP.Suite` against the tool's own input JSON Schema. That
   validation is version-independent and is reached unchanged.

This is honest for a four-method surface and no more. It does not scale: every
method added means more hand-written guards, and the translation reads raw maps
where a generated vocabulary would give struct-to-struct conversion. Generating
`V2511` entities is what replaces layers 1 and 2 with a real validator, and is
the natural next slice — see the feature document.

## Design

### Request path

A 2025 POST is translated into the *same* per-request worker contract the 2026
transport already drives (`GenMCP.Server.start_request/3` +
`GenMCP.Mux.Channel`), so `GenMCP.Suite` (`lib/gen_mcp/suite.ex:240`) and every
provider stay single-sourced on `V2607`.

The 2025 request carries no `_meta` protocol context. The plug synthesizes it
from the session: the negotiated version, client name and version sealed in the
session id are written into the `V2607` request's
`params._meta.io.modelcontextprotocol/*` keys before dispatch, so
`Channel.from_request/3` (`lib/gen_mcp/mux/channel.ex:114`) populates
`channel.meta` exactly as it does for a 2026 request. Handlers reading
`channel.meta.client_info` keep working.

`initialize` is the one method that never reaches a worker: the plug answers it
itself, because the 2026 core has no equivalent (`server/discover` is a
different shape and needs no handshake). Its capabilities come from a
`server/discover` run through the normal worker path, translated down to a 2025
`ServerCapabilities`.

### Method surface

| 2025 method                 | Handling                                                    |
| --------------------------- | ----------------------------------------------------------- |
| `initialize`                | Answered by the plug. Mints `Mcp-Session-Id`.               |
| `notifications/initialized` | `202`, no worker.                                            |
| `ping`                      | `{}` result, no worker.                                      |
| `tools/list`                | Translated to `V2607.ListToolsRequest`.                      |
| `tools/call`                | Translated to `V2607.CallToolRequest`.                       |
| anything else               | `-32601` method not found.                                   |

`{:input_required, ...}` (MRTR) has no 2025 equivalent. Per the feature
document this is an invalid callback return on this transport: the worker
crashes and the relay converts it to an internal error, never telling the
client its request was faulty.

### GET is a subscription

The 2025 GET SSE stream is served by mapping it onto the Suite's
`subscriptions/listen`. The plug builds a `V2607.SubscriptionsListenRequest`
with every filter flag requested, runs it through `GenMCP.Server` like any other
request, and streams the result — the handler narrows to what it actually
serves via its honored filter.

The stream is then filtered on the way out, because a 2025 client does not know
the 2026 subscription vocabulary:

- `notifications/subscriptions/acknowledged` is dropped.
- `_meta.io.modelcontextprotocol/subscriptionId` is stripped from every
  forwarded notification.
- The terminal `SubscriptionsListenResult` ends the stream instead of being
  sent — a 2025 GET stream has no request id to answer.
- The `list_changed` / `resources/updated` notification method names are
  identical across both versions, so they forward untouched.

With no `:subscription_handler` configured, or when the handler rejects the
subscription, GET answers `405 Method Not Allowed` — which the 2025 spec
permits.

`DELETE` is a no-op `200`: the default session holds no server-side state.

### Session controller

`GenMCP.SessionController`, a behaviour with two operations:

- `create(session, conn, arg)` on `initialize`
- `fetch(session_id, conn, arg)` on every later request

Argument order follows the Suite provider convention: subject first, `arg` last.

The default `GenMCP.SessionController.Token` stores nothing server-side — the
session id *is* the session, sealed with `GenMCP.Token`. This needs a new
`{:session, _}` purpose in `GenMCP.Token`, alongside the existing `:cursor` and
`:reqstate`. Fetch is a decrypt. The sealed payload is the pruned tuple from
the feature document:

    {1, negotiated_vsn, client_name, client_version}

### Shared SSE relay

The receive loop, keepalive, chunking and finalization currently inside
`GenMCP.Transport.StreamableHTTP.Impl` (`streamable_http.ex:448-664`) are
version-agnostic. They move to `GenMCP.Transport.Relay`, parameterized by a
codec that decides how each worker message is rendered:

- `Relay.Codec.JSONRPC` — current behaviour, used by 2026 and by 2025 POST.
- the GET-stream codec described above.

The existing 2026 transport tests are the safety net for this move: they must
stay green untouched.

## Acceptance — met

All six criteria are covered by `test/gen_mcp/v2511_compat_test.exs` (36
tests), with the 2026 suite untouched and green throughout.

- A 2025 client completes `initialize` → `notifications/initialized` →
  `tools/list` → `tools/call` against a Suite configured only with 2026 tools,
  with no 2026-specific code in the tool. — the handshake, 202 and round-trip
  tests, plus "a tool sees a 2026 request and the client info sealed in the
  session", which asserts the tool receives a `V2607.CallToolRequest`.
- A streaming tool's progress and log notifications arrive on the POST's own
  SSE response. — one test each; the log one came out of review finding 1.
- A session id round-trips; a forged, tampered, or absent one is rejected. —
  four tests, plus lifetime configuration.
- GET opens a subscription stream and delivers a `list_changed` notification
  with no 2026 subscription vocabulary leaking into it. — "serves
  notifications from the subscription handler with no 2026 vocabulary".
- GET answers 405 when no subscription handler is configured. — covered, and
  separately that a mid-stream crash ends the stream rather than writing a
  bogus 405 payload into it (review finding 2).
- The whole existing 2026 suite stays green. — the relay extraction was
  validated against the untouched 2026 transport tests.

Beyond the original list: the hand-written envelope validation (malformed
`params`, non-scalar `id`, bad `arguments`, junk `_meta`), `logging/setLevel`,
2026 reserved `_meta` stripping, subscription-id stripping in both struct and
string-keyed shapes, and client-disconnect teardown.

## Resolved during review

- **Logs flow.** Feature 017 puts log notifications on the POST stream in
  scope, so the synthesized request `_meta` carries a default log level
  (`:info`). Without it `Channel.send_log/4` drops every record and the
  `logging` capability advertised at `initialize` is a promise never kept.
- **Errors on an open stream.** A codec cannot tell "nothing written yet" from
  "stream already open", so the relay asks two different questions:
  `render_error/3` (an HTTP status is still available) and
  `render_stream_error/3` (the response is an SSE stream). The GET stream
  answers `:end` to the second — a 2025 client reads bare notifications there,
  so any error payload would be parsed as one.
- **Session lifetime is one day**, set by the controller rather than inherited
  from `GenMCP.Token`'s 20 minutes, which is sized for a pagination cursor. It
  was already configurable through the controller `arg`
  (`{GenMCP.SessionController.Token, max_age: 3600}`), only undocumented.
- **2026 reserved `_meta` keys are stripped** from downgraded results, both the
  `io.modelcontextprotocol/*` block the Suite adds and the subscription id the
  channel stamps onto notifications.

- **`logging/setLevel` is accepted and ignored**, resolving the feature
  document's open question. A client sets its level during setup and has no
  reason to expect a failure, so answering a JSON-RPC error would break
  sessions over a setting rather than over anything the client did wrong. The
  requested level cannot be honored — the token session is immutable — so what
  the client gets is the default level the transport synthesizes.
- **A dropped connection notifies the worker.** When a write fails because the
  client is gone, the relay sends `{:"$gen_mcp", :closed}` before finalizing,
  so `handle_close` cleanup is tied to the failed write rather than to the
  connection process exiting afterwards. Belt and braces: the `:CHAN_DOWN`
  monitor already covers this under Bandit, and no test distinguishes the two.

## Open, deferred to later slices
- Token encryption requires Phoenix. `Phoenix.Token` resolves a `Plug.Conn`
  through `phoenix_endpoint`, so mounting the compat transport in a plain Plug
  router raises `KeyError` at `initialize`. This affects cursors and MRTR on
  the 2026 transport too, so it is being scoped as its own feature.
- Resources and prompts methods.
- `V2511` codegen, `gen_mcp2` packaging.
