# Barebones 2025 stateful spec compatibility

Retrofitting support for the current 2025 stateful MCP spec (2025-06-18 /
2025-11-25) on top of the stateless 2026-07-28 core.

Started as a backlog reflection. Spec 018 built the thing and is done, so the
design question ("can a 2025 client be served by translating at the transport
boundary, leaving the Suite and providers untouched?") is answered: yes.

**Feature complete (2026-07-29).** The compat transport was deployed on a
production server serving real 2025 clients and works as built — the surface
spec 018 covers is the surface our servers need. Every open decision below is
resolved; nothing further is planned here. What remains is the release itself,
which lives in spec 006.

## Status

### Done — spec 018

- [x] Separate compat plug `GenMCP.Transport.StreamableHTTP.V2511`, mounted on
      its own path, with `defplug/1` for routers that forward a module once.
- [x] SSE machinery extracted to `GenMCP.Transport.Relay` and shared with the
      2026 transport, parameterized by a codec per response shape. The 2026
      transport's own tests were the safety net and stayed green untouched.
- [x] Translation at the boundary: a 2025 body becomes a `V2607` struct and
      runs the same `GenMCP.Server` worker contract, so `GenMCP.Suite`, tools
      and every provider stay single-sourced on 2026 vocabulary and never learn
      a 2025 client exists.
- [x] Request `_meta` synthesized from the session, so `channel.meta` carries
      client info and the negotiated version exactly as for a 2026 request.
- [x] `GenMCP.SessionController` behaviour + data-bearing token default
      (`{1, vsn, name, version}` sealed with `GenMCP.Token`); `DELETE` is an
      accepted no-op; missing session -> 400, unknown/expired -> 404.
- [x] `initialize` with version negotiation (unknown version answers the newest
      supported), `notifications/initialized`, `ping`.
- [x] `tools/list` and `tools/call`, with progress and log notifications on the
      POST's own SSE response.
- [x] GET stream mapped onto `subscriptions/listen`, with the 2026 subscription
      vocabulary stripped on the way out; `405` when no handler is configured.
- [x] MRTR `{:input_required, ...}` becomes an internal error, never a client
      fault.
- [x] Envelope validation by hand (no `V2511` validator): `id` scalar, `params`
      an object, `arguments` an object, malformed `_meta` ignored.
- [x] 2026 reserved `_meta` keys stripped from downgraded results.

Resolved along the way, and recorded below: `logging/setLevel`
(accept-and-ignore), session TTL (one day), the GET stream (subscription rather
than a flat 405).

### Decided — after the production deployment (2026-07-29)

- [x] **Is the method surface enough?** Yes. A production server serving real
      2025 clients needs exactly `initialize`,
      `notifications/initialized`, `ping`, `logging/setLevel`, `tools/list`,
      `tools/call` and the GET stream. Resources and prompts were never
      exercised — they stay unbuilt. Should a user report needing them, each
      is a `Translate` clause plus a route: reopen this feature with one spec
      per method family rather than pre-building for a hypothetical.
- [x] **Generate `V2511` entities?** No. The trigger was "the surface grows
      enough that hand-written guards stop being honest", roughly once
      resources and prompts land. The surface did not grow, so the
      hand-written envelope validation in the plug plus the `Translate` guards
      remain proportionate. Codegen stays documented below as the drop-in
      replacement if that ever changes.
- [x] **Do both protocols need one URL?** No. Separate mount paths were what
      the production migration used, and it was enough. The sniffing
      dispatcher plug sketched below is not built and is not planned.
- [x] **`gen_mcp2` packaging** — not needed, dropped. Its whole rationale was
      endpoint-by-endpoint migration inside one app when two gen_mcp versions
      must coexist. The compat transport removes that need: an app upgrades to
      v2 wholesale and swaps the plug on its existing 2025 routes, which is
      what the production server did and what `guides/090.upgrading-to-v2.md`
      documents. No second hex package, no rename pipeline, no name-collision
      audit.
- [x] **v1 / v2 release split** — the compat layer ships as part of v2, not as
      its own major. Decision and remaining release work move to spec 006.
- [x] **Phoenix requirement.** Accepted as-is for this feature: the migrating
      servers are Phoenix apps, so `GenMCP.Token` resolving through
      `phoenix_endpoint` was never a blocker in production. The plain-Plug
      case remains feature 019 (backlog), and it is a v2 limitation to state
      in the release notes, not a release blocker.
- [x] **Keep or drop the spike.** Kept. Spec 018's shape held under a real
      server, so it stops being a spike and becomes the shipped compat
      transport.

### Noticed while writing this list — not 2025-specific

- [x] Mount examples omitting the required `:server_name` and
      `:server_version`, including the one billed as "the smallest useful
      mount". Copying one produced a `500` on every request rather than a
      boot-time error, because the Suite's `init/1` runs per request under the
      stateless core. Fixed: eight examples in `streamable_http.ex` and the
      four V2511 ones written for this feature. Examples passing `:server`
      were already correct — they bypass the Suite, so its required options do
      not apply. Audited across `lib/`, `guides/` and `README.md`; the
      provider docs, guides and README were already right.

## Purpose and scope

The only goal is to **keep existing 2025 tool calls working while we migrate
our servers** to the stateless core. This is a migration shim, not feature
parity:

- Supported: `initialize` handshake, `notifications/initialized`, `tools/list`,
  `tools/call` (with the usual progress/log notifications on the POST's own SSE
  response), and whatever list/read/get methods our migrating servers actually
  use.
- Everything stateful-fancy is out: no resumability (`Last-Event-ID`), no
  server-initiated requests (sampling/elicitation), no `resources/subscribe`.
- Tool `{:input_required, ...}` returns (MRTR) have no 2025 equivalent. On the
  compat transport this is an **invalid callback return** — a server-side
  contract violation, not a client fault. The worker crashes (as for any
  invalid return), and the transport converts the crash into a JSON-RPC
  internal error, the same way the existing `:server_crashed` path does. The
  client must not be told its request was faulty.
- 2026-only methods (`server/discover`, `subscriptions/listen`) are rejected
  naturally: the 2025 validator does not know them.

The `main` branch still holds the full pre-fork stateful implementation and is
the reference / salvage source for all of this.

## Current choices

### Vocabulary: regenerated `V2511` entities — NOT built

The original plan: reintroduce the old vocabulary as a generated
`GenMCP.MCP.V2511` module set (2025-11-25 schema, which also serves 2025-06-18
clients) living next to `V2607`, with a `V2511` validator selecting the 2025
request surface. The codegen tooling supports versioned namespaces, though
`tools/gen-rpc-schemas.exs` currently hardcodes `mod_prefix: GenMCP.MCP.V2607`
and `mix.exs` would need a second schema ref.

Spec 018 skipped it. For a surface this small the 2025 shapes are close enough
to their 2026 counterparts that a hand-written translation is smaller than the
generated vocabulary it would consume, and skipping codegen was the fastest way
to answer the design question. The cost is that validation is hand-written and
does not scale: the JSON-RPC envelope is checked once in the plug, the few
fields the shim reads are guard-checked in `Translate`, and the part that
actually matters — tool arguments — is validated downstream by `GenMCP.Suite`
against the tool's own input schema, which is version-independent.

Codegen remains the drop-in replacement for those first two layers if the
surface grows.

### Second transport layer

A separate legacy plug (e.g. `GenMCP.Transport.StreamableHTTP.V2511`) rather
than branching inside the current one: header rules, the `initialize` special
case, and session lookup differ too much. The SSE machinery
(`stream_loop`/keepalive/finalize in the current `Impl`) is version-agnostic
and gets extracted and shared. Requests are translated at this boundary into
the per-request worker contract the stateless core already runs, so the Suite
and the provider behaviours stay single-sourced.

If both protocols must share one URL, a thin dispatcher plug sniffs
(`MCP-Protocol-Version: 2026-07-28` header vs `initialize` body) and delegates.

### Simplified session controller

A small behaviour with two operations: **create** on `initialize`, **fetch** on
every subsequent request. Session state is written once and only read
afterwards — it stores the client initialization parameters the server actually
reads later, nothing more.

### Data-bearing session id (default controller)

The default implementation stores nothing server-side: the `Mcp-Session-Id`
**is** the session data, sealed with `GenMCP.Token` (already in the codebase,
cluster-safe via `secret_key_base`). Fetch = decrypt. `DELETE` is a no-op
accept. No revocation; sessions expire by token TTL only.

To keep the header small (budget: cookie-sized, a few hundred bytes — well
under proxy per-header limits), we encode a pruned tuple, not the full
initialize params (`clientInfo` is unbounded: descriptions, icon data URIs...):

    {1, negotiated_vsn, client_name, client_version}

The leading `1` is a mere 8-bit integer tag. Later gen_mcp releases will not
have session ids at all, so no versioning scheme is needed beyond this.

Deployments that need the full `clientInfo`/capabilities server-side, or real
revocation, plug their own storage-backed controller via the behaviour. Since
the default holds no process and no table, the earlier idea of an optional
`:syn` dependency for an in-memory default is superseded — nothing needs a
registry.

### GET stream — built as a subscription

Plan A was to answer `405 Method Not Allowed` and see whether any client
minded, since the 2025 spec permits it and tool-call progress/logs ride the
POST response stream rather than the GET one. Built instead as the fallback
that plan named: GET runs a `V2607.SubscriptionsListenRequest` through the
ordinary worker path, so the Suite's configured `:subscription_handler` serves
it, and the 2026 subscription vocabulary is translated away on the wire — the
`acknowledged` notification dropped, subscription ids stripped, the terminal
`SubscriptionsListenResult` ending the stream rather than being sent.

`405` remains the answer when no handler is configured, so plan A is still what
a server that does not want the stream gets, by doing nothing.

## Release strategy — superseded, see spec 006

> The plan below is kept for the reasoning it records. It is **no longer what
> we are doing**: the `gen_mcp2` package is dropped (the compat transport
> removes the need for two coexisting packages), and the v1/v2 split is now
> owned by spec 006. Read this section as history.

- The existing stateless code ships as **v1**.
- This retrofit, if done, ships as **v2** (stateless core + compat layer).
- In parallel, a **temporary `gen_mcp2` hex package** with all modules renamed
  `GenMCP2.*`. Rationale: Mix cannot install two versions of one package and
  both claim the `GenMCP.*` namespace, so without it a dep bump forces porting
  every endpoint in one commit. `gen_mcp2` allows endpoint-by-endpoint
  migration inside one app: implement new services against the `2` package,
  then once the old dependency is removed, mass-rename `GenMCP2` → `GenMCP`
  and swap the dep — it lands on identical code.

`gen_mcp2` is generated, never hand-maintained: a release script textually
rewrites `GenMCP` → `GenMCP2` and `:gen_mcp` → `:gen_mcp2` across the tree and
runs the full test suite on the renamed copy. Name-load-bearing spots to audit:
telemetry event prefixes, the registered `GenMCP.ServerSupervisor` name (both
apps must boot in one VM), `Application.get_env(:gen_mcp, ...)` keys. Publish
with a "temporary migration package" notice, version-locked to the `gen_mcp`
v2 release it is generated from; retire after our migrations.

## Questions answered by the spike

- **`logging/setLevel`** — accept and ignore, answering `{}`. A client sets its
  level during setup and has no reason to expect a failure, so a JSON-RPC error
  would break sessions over a setting rather than over anything the client did
  wrong. The requested level cannot be honored (the token session is
  immutable), so what a 2025 client gets is the default level the transport
  synthesizes into every request.
- **Default token TTL for sessions** — one day, set by the session controller
  rather than inherited from `GenMCP.Token`'s 20 minutes, which is sized for a
  pagination cursor replayed within one listing rather than a session held
  across a whole conversation. Configurable per mount through the controller
  arg.
- **The MRTR question** — confirmed as specced: an `{:input_required, ...}`
  return is an invalid callback return on this transport, the worker crashes,
  and the relay converts it into an internal error. The client is never told
  its request was faulty.

The remaining open items are the checkboxes at the top.

## Effort notes (from codebase review, 2026-07-15)

Rough shape of the work: `V2511` entities regeneration (small), legacy
transport + shared SSE extraction (medium, much salvageable from `main`),
session controller + token default (small once data-only), request/result
translation 2025 ↔ core contract (the fiddly heart), `gen_mcp2` release
pipeline (small, mostly scripting + audit). The old stateful test suite on
`main` (~3k lines) is re-targetable for the compat transport.

### How it actually went (2026-07-25)

The estimate held where it mattered and was wrong in one place. The SSE
extraction was smaller than "medium" — the loop was already version-agnostic,
so it moved almost verbatim behind a codec hook. The session controller and
token default were indeed small. Translation was correctly identified as the
fiddly heart, and it is where every review finding landed: `_meta` handling on
both directions, subscription-id stripping, and the validation that a generated
vocabulary would otherwise have provided.

Nothing was salvaged from `main` in the end — the per-request worker contract
differs enough from the stateful one that translating into the new contract was
cleaner than adapting old code. The `main` test suite was likewise not
re-targeted; the compat tests were written fresh against the 2025 wire format
(36 tests), deliberately not using `GenMCP.Test.Client`, which validates
outgoing messages against the 2026 schemas a 2025 client does not speak.
