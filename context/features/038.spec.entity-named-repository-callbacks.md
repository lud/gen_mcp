# Entity-named repository callbacks

## Goal

Name the repository callbacks after the entity they act on, so that one module
can implement several repository behaviours without two callbacks sharing a
name, and so that the skill callbacks (`list_skills/3`, `get_skill/3`) follow
the common scheme instead of being the exception.

## Context

`GenMCP.Suite.ResourceRepo` and `GenMCP.Suite.PromptRepo` both define `list/3`.
A skill repository implements `ResourceRepo` and `SkillRepo` in one module,
which is why spec 036 had to name its listing callback `list_skills/3`. Every
future protocol extension that brings its own repository behaviour would meet
the same collision.

## Design

### Layering

An extension repository builds on a base behaviour instead of redeclaring its
callbacks. `SkillRepo` requires the implementing module to be a `ResourceRepo`
too, and declares only its own callbacks. Future extensions that serve
resources do the same, so several of them can live in one module with
`ResourceRepo` as their common ground: `prefix/1`, `read_resource/3` and
`cache_control/1` are declared once.

This holds only if every extension behaviour names its own callbacks after its
entity. Two extensions on the same base that both declared a bare `list/3`
would conflict.

Extensions that do not build on the same base have no common ground. Their
shared callback names (`prefix/1`, `cache_control/1`) conflict when one module
implements both, as `ResourceRepo` and `PromptRepo` do today.

### Renames


| Behaviour      | Today    | New                |
| -------------- | -------- | ------------------ |
| `ResourceRepo` | `list/3` | `list_resources/3` |
| `ResourceRepo` | `read/3` | `read_resource/3`  |
| `PromptRepo`   | `list/3` | `list_prompts/3`   |
| `PromptRepo`   | `get/4`  | `get_prompt/4`     |
| `SkillRepo`    | `list_skills/3`, `get_skill/3` | unchanged |

Arguments and return values do not change.

The behaviour modules already export `ResourceRepo.list_resources/3` and
`ResourceRepo.read_resource/3`, the functions the Suite calls with a
descriptor. They keep their names: the callback lives on the implementation
module and the dispatch function on the behaviour module, as
`GenMCP.Suite.Extension` already does with `tools/2`.

Backwards compatibility: the Suite calls the new name when the module exports
it, and falls back on the old name otherwise. Existing repositories keep
working unchanged. The old callbacks stay in the behaviours as optional,
documented as the former names.

`GenMCP.Suite.SkillRepo.Static` and the documentation and guides use the new
names only.

## Open questions

- **Shared callbacks.** `prefix/1` and `cache_control/1` are defined by both
  `ResourceRepo` and `PromptRepo`. Checked on Elixir 1.20.2 with two
  behaviours declaring the same callback:
  - `@impl true` is accepted, and so is `@impl OneOfTheTwo`.
  - A function takes a single `@impl`. A second one replaces the first and
    warns `redefining @impl attribute`.
  - Whatever `@impl` says, the compiler warns `conflicting behaviours found.
    Callback function prefix/1 is defined by both A and B` for every callback
    the two behaviours share, optional and unimplemented ones included. There
    is no way to silence it from the implementing module.

  So a module implementing `ResourceRepo` and `PromptRepo` together cannot
  compile without warnings as long as they share a callback name. Skill
  repositories are not concerned: `SkillRepo` declares only its own two
  callbacks and relies on `ResourceRepo` for the rest. To decide: rename the
  shared callbacks per entity as well, move them to one common behaviour that
  both repositories include, or accept that resource and prompt repositories
  stay separate modules.
- **Deprecation.** Does the fallback on the old names warn, and is there a
  version where it is removed?
- **`use` macros and mocks.** Which generated or overridable functions
  (`defoverridable` in `SkillRepo.Static`, the test mocks) must follow the
  rename.

## Acceptance criteria

- [ ] A repository implementing only the new names is served.
- [ ] A repository implementing only the old names is served unchanged.
- [ ] A module implementing `ResourceRepo`, `PromptRepo` and `SkillRepo` at
      once compiles with no callback sharing a name between the entity-specific
      operations.
- [ ] Documentation and guides show the new names.
