# Bad jsonrpc version answers a non-protocol error code

`GenMCP.Error` answers `:bad_rpc_version` with JSON-RPC code **`1`**
(`error.ex:141`, `defcasterror :bad_rpc_version, 1, 400`). Both transports
raise that reason when a request body carries a `jsonrpc` member that is not
`"2.0"` (`streamable_http.ex:329`, `v2511.ex:253`).

`1` is not a JSON-RPC code and not an MCP one. A malformed `jsonrpc` member is
what JSON-RPC 2.0 calls an Invalid Request, which is `-32600` — the code the
neighbouring `:bad_rpc` clause already answers with. No test pins the current
value, and it reaches the wire on both transports.

Found while moving the error codes onto the generated schema registry
(`Info.error_codes/0`): that change covers every code read from the spec, and
this is the one literal it does not reach, because no schema definition
allocates it.

## Fix — done

`:bad_rpc_version` answers `@rpc_invalid_request` (`InvalidRequestError`,
`-32600`) and keeps its `400` status. The message stays
`"Invalid RPC version, only 2.0 is accepted"`, which is now the only thing
separating it from `:bad_rpc` — that is the JSON-RPC 2.0 reading: both are
Invalid Request.

Pinned on both transports: `streamable_http_test.exs` "sending a jsonrpc
version other than 2.0" and `v2511_compat_test.exs` "answers -32600 for a
jsonrpc version other than 2.0", each asserting the code and the message.

## Follow-up to consider

The registry is now the source for every code `GenMCP.Error` emits except this
one. Once it is gone, a check that no clause states a bare literal would keep
the file that way — worth weighing against just reading the module.
