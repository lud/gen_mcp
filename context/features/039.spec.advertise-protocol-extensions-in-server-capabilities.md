# Advertise protocol extensions in server capabilities

## Goal

Let a server declare the MCP protocol extensions it supports, so they appear in
`capabilities.extensions` of `server/discover`. Today the only entry a gen_mcp
server can emit is the skills extension.

Advertising is a declaration and nothing more: an extension identifier mapped
to a settings object. The work an extension implies lives elsewhere (the
authorization server for the auth extensions, tool `_meta` and `ui://`
resources for MCP Apps).

## Context

### What the settings objects contain

The value under each identifier is defined by that extension.

| Extension | Identifier | Server settings |
| --- | --- | --- |
| Skills | `io.modelcontextprotocol/skills` | `directoryRead` (boolean, default `false`): the server implements `resources/directory/read` |
| MCP Apps | `io.modelcontextprotocol/ui` | None. `mimeTypes` exists on the **client** side only |
| Tasks | `io.modelcontextprotocol/tasks` | None (`Record<string, never>` in the schema) |
| OAuth Client Credentials | `io.modelcontextprotocol/oauth-client-credentials` | None. Its specification does not mention capabilities; the docs show `{}` |
| Enterprise-Managed Authorization | `io.modelcontextprotocol/enterprise-managed-authorization` | None. Same as above |

The extensions overview adds one generic key: an Experimental or Beta extension
that makes a breaking change should add or increment a `revision` string in its
settings. No extension above uses it yet.

### How MCP Apps is negotiated in practice

The Apps specification only describes the client declaring support, and the
server checking that declaration. Hosts find UI through `_meta.ui.resourceUri`
on tools.

- `registerAppTool` and `registerAppResource` in the official
  `@modelcontextprotocol/ext-apps` server helpers do not advertise the
  extension.
- PR #79 runs Apps through the 2025 compat transport behind Claude Desktop (see
  spec 024), and that transport has never sent `extensions`.
- The extensions overview does show a server advertising
  `io.modelcontextprotocol/ui` with `{}`, and `server/discover` lets a client
  present what a server supports.

Closed-source hosts cannot be checked beyond this.

### Current code

- `GenMCP.Suite` builds `extensions` in its private `capabilities/2`, from
  whether any provider returns skill repositories.
- `:extensions` is already a Suite option, and means
  `GenMCP.Suite.Extension` provider modules.

## Design

### `:protocol_extensions` Suite option

A map of extension identifier to settings object, empty by default:

```elixir
forward "/mcp", GenMCP.Transport.StreamableHTTP,
  server_name: "My App",
  server_version: "1.0.0",
  protocol_extensions: %{
    "io.modelcontextprotocol/oauth-client-credentials" => %{}
  }
```

The entries are merged with the entries the Suite computes. When the result is
empty, `extensions` stays `nil` and is left out of the response, as it is today.

The option is for extensions that add no JSON-RPC method. The Suite has no route
for methods it does not know, so declaring Tasks here would promise methods
nothing answers.

## Out of scope

- The 2025 compat transport, which receives no new features. Its `initialize`
  result keeps leaving out `extensions`.
- Implementing Tasks or any extension that adds methods.
- Helpers for declaring UI tools and `ui://` resources.
- An authorization server, or any token handling (spec 027 covers the resource
  server side).

## Open questions

1. **Should MCP Apps be advertised without configuration?** Nothing forbids
   advertising it, and advertising does not oblige the server to serve any UI.
   - *Always on:* the simplest, but every gen_mcp server then reports Apps
     support, including to clients presenting capabilities from
     `server/discover`.
   - *Derived from tools (recommended):* advertise it when a tool exposed to the
     request has `_meta.ui.resourceUri`, as skills are derived from skill
     repositories. It needs expanding the tools during discovery, like
     `tools/list`, and reading `_meta` with atom or string keys. A tool offered
     only to clients declaring Apps can be missed, because `server/discover` may
     carry empty client capabilities. Such a server declares the identifier
     through the option.
2. **Should the option accept a shorter form?** No server setting exists outside
   skills, which the Suite manages, so maps are mostly `=> %{}`. Recommended: a
   list whose entries are an identifier or an `{identifier, settings}` tuple.
3. **How are entries validated?** Identifiers must follow the `_meta` key rules
   with a mandatory prefix. Recommended: check them at init and reject
   `io.modelcontextprotocol/skills`, which only the Suite can truthfully declare.

## Acceptance criteria

- Entries of `:protocol_extensions` appear in `capabilities.extensions` of
  `server/discover`, next to the skills entry when skills are provided.
- Without entries or skills, `extensions` is absent from the response.
- The 2025 `initialize` result is unchanged.
