# Release packaging + migration docs

Ship the fork. Every build spec under feature 001 is done, and feature 017
(2025 compat transport) closed on 2026-07-29 after running on a production
server against real 2025 clients. This spec is now the only thing between the
work and a release.

## Packaging decision — resolved 2026-07-29: single package

The feature-level open question was: does any downstream client platform send
different-version requests to the **same** server endpoint? It turned out to be
answerable without packaging at all.

Feature 017's compat transport
(`GenMCP.Transport.StreamableHTTP.V2511`) serves 2025 clients from the same
application, on their existing route, as a separate plug mount. A production
server ran it against real 2025 clients and needed nothing more. So one app can
field both protocols on one `gen_mcp` version:

- **Single `gen_mcp` package.** No frozen legacy package.
- **No `gen_mcp2`.** Its only rationale was endpoint-by-endpoint migration when
  two gen_mcp versions must coexist in one app; the compat transport removes
  that requirement, and with it the rename pipeline and the
  name-collision audit (telemetry prefixes, `GenMCP.ServerSupervisor`,
  `:gen_mcp` env keys).

## Version numbers — v1 stateful, v2 stateless

Both hard constraints on cutting majors are now satisfied:

- **Implementation done** — specs 002-005, 007, 008, 011, 013, 014, 016, 020,
  022 and feature 017 are all done.
- **Schema fixed** — `mix.exs` pins `ref: "2026-07-28"` with
  `sparse: "schema/2026-07-28"` (locked at `5f5440bb`). The moving
  `schema/draft` vendoring is gone, so the version is no longer a target that
  can shift under a released major.

Therefore:

- **`1.0.0`** — the current stateful line, tagged from `main` as it stands
  today (`0.10.0` plus dependency bumps). It exists to give stragglers a
  supported `~> 1.0` lane, not to add anything.
- **`2.0.0`** — the stateless core plus the 2025 compat transport, from
  `feat/new-specs` merged into `main`.

`guides/090.upgrading-to-v2.md` already documents the upgrade in these terms
(dependency `~> 2.0`, plug swap on the existing route), so the numbering is
committed to in the docs and should not be revisited.

## Maintenance branch

- Branch `1.x` from the `v1.0.0` tag, **on demand only** — there is nothing to
  backport yet, and the tag is enough to create the branch whenever there is.
- Backport policy: security fixes and dependency-compatibility fixes only. No
  features, no protocol work. The 2025 protocol is frozen; anyone needing it
  served on a maintained lane should upgrade to v2 and mount the compat
  transport.

## How a release is cut

Established while cutting `1.0.0` on 2026-07-29, and the procedure `2.0.0`
should follow. `mix version` was **not** used: its `before_commit` hook runs
`git cliff --tag vsn -o CHANGELOG.md` with no way to pass release prose, so the
steps are manual until mix_version issues
[#77](https://github.com/lud/mix_version/issues/77) (`--annotation-file`) and
[#78](https://github.com/lud/mix_version/issues/78) (arity-2 hooks receiving
the token) land.

Release notes live in the **annotated tag message**. `cliff.toml`'s body now
renders `{{ message }}`, and git-cliff reads annotated tag messages by itself,
so the note survives any later full regeneration — verified: after tagging,
`git cliff --tag v1.0.0` with no flags reproduced `CHANGELOG.md` byte for byte.
The template filters messages starting with `new version`, so the boilerplate
annotations `mix version` wrote on older tags stay out of the changelog.

The sequence, with the prose written once to `tmp/note.md` (gitignored):

1. Bump `@version` in `mix.exs`.
2. `mix rdmx.update README.md` and the guides — **do not skip.** Without
   `mix version` the readmix hook never runs, and 1.0.0 was nearly published
   telling users to install `~> 0.10`.
3. `git cliff --tag vX.Y.Z --with-tag-message "$(cat tmp/note.md)" -o CHANGELOG.md`
   — the flag is needed because the tag does not exist yet.
4. Commit, then `git tag -a vX.Y.Z -F tmp/note.md`.

      it. Verified: 122 modules, no `test/support` module in the sidebar,
      both guides present.
