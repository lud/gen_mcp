# Enforce required client capabilities

The 2026-07-28 base protocol makes this a MUST:

> A server **MUST NOT** rely on capabilities the client has not declared. If
> processing a request requires a capability the client did not include in
> `io.modelcontextprotocol/clientCapabilities`, the server **MUST** return a
> `MissingRequiredClientCapabilityError` (`-32021`) whose
> `data.requiredCapabilities` lists the missing capabilities. On HTTP, the
> response status **MUST** be `400 Bad Request`.

We parse `clientCapabilities` off the request `_meta` into `channel.meta`
(`mux/channel.ex:173`) and hand it to handlers, and never enforce anything.
`-32021` is never emitted — the code is already in the generated registry
(`GenMCP.MCP.V2607.Info.error_codes/0`), unused.

Surfaced while reviewing PR #81, which fixed the two codes we did have wrong.
The same schema registry named a third one we had never implemented.

## Where it bites

MRTR. A handler returning `{:input_required, ...}` asks the client for
elicitation, sampling or roots — capabilities a client declares. Today that
result goes out to a client that never declared it, and the client is entitled
to have no idea what to do with it.

## To decide

- **Who checks.** The transport cannot know which capability a request needs;
  only the handler that is about to need it does. Likely shapes: the Suite
  checks before dispatching an MRTR result, or `GenMCP.Mux.Channel` grows a
  `require_capability/2` a handler calls and that raises the error reason.
- **What `data.requiredCapabilities` holds.** The spec says "lists the missing
  capabilities"; settle on the wire shape (a list of capability names) and the
  internal reason tuple that carries it into `GenMCP.Error`.
- **The 2025 compat transport.** `Translate.request_meta/2` synthesizes an
  empty `%MCP.ClientCapabilities{}` for every 2025 request
  (`v2511/translate.ex:183`), so enforcement there would reject every MRTR
  result. Feature 017 already rules MRTR an invalid callback return on that
  transport, so the two need to agree rather than each raise their own error.

## Acceptance

- A request whose `_meta` omits a capability the handler requires is answered
  `-32021` at HTTP 400, with `data.requiredCapabilities` naming it, and the
  handler's result never reaches the wire.
- A request that declares the capability is unaffected.
- The 2025 compat transport keeps answering an internal error for MRTR, not
  `-32021`.
