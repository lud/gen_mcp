# `Channel.start_stream/1` + collapse the channel status

Spun out of GitHub issues #74 and #75.

## The problem

A tool doing slow work synchronously in `c:GenMCP.Suite.Tool.call/3` writes
nothing until it finishes, so it never gets the 25s `:keepalive` chunks that
`GenMCP.Transport.Relay` sends on an open stream. Any proxy, load balancer or
client idle timeout in the path kills the request where the keepalives would
have held it open. This is a silent regression from the 0.10 `{:async, ...}`
return, which opened the SSE response as a side effect.

There is currently no way to say "open the stream now, then keep working". The
two things that do open it both come with baggage:

- Returning `{:stream, state}` opens it, but means "I will be fed messages" —
  it forces the work into `c:GenMCP.Suite.Tool.handle_message/4` and the request
  data to be threaded through a state term to get there. The known trick is
  `send(self(), :continue)` before returning `{:stream, request}`.
- `GenMCP.Mux.Channel.send_progress/4` and `send_log/4` open it as a side
  effect of the notification they send (`Relay.stream_loop/1` calls
  `init_stream/1` on `{:"$gen_mcp", :notification, _}`), but each is a no-op
  when the client supplied no progress token / no log level, so neither is a
  reliable trigger.

Issue #75 proposed a `{:continue, state}` return plus a new callback. Rejected:
it adds a callback (or a magic message) for what is one imperative act, it still
requires the reader to know the framework opens the stream before calling back,
and it would have to be added to every callback's return union separately
(`Tool.call/3`, `GenMCP.handle_request/3`, `SubscriptionHandler`) instead of
working anywhere a channel exists.

## The change

### 1. `Channel.start_stream/1`

Switch the response to stream mode from anywhere a channel is in hand:

```elixir
def call(req, channel, _arg) do
  :ok = Channel.start_stream(channel)
  {:result, MCP.call_tool_result([run(req)])}
end
```

It sends `{:"$gen_mcp", :stream}` to `channel.client`, which is exactly what
`GenMCP.Server` already does on a `{:stream, state}` return
(`server.ex:168-171`). The relay's `init_stream/1` has a `:streaming` no-op
clause, so repeat calls and a later `send_progress/4` are harmless and produce
one stream.

Returns `:ok`, not `{:ok, channel}`: there is nothing on the struct to update
(see below), and tool callbacks do not hand the channel back. Returns
`{:error, :closed}` on a closed channel, like the other send functions.

Name: `close/1` acts on the channel lifecycle, `start_stream/1` on the
response mode. They are not counterparts and should not be named as if they
were.

### 2. Collapse `status` to `:open | :closed`

`@type status :: :request | :stream | :closed` conflates two orthogonal axes —
channel lifecycle and response mode — which is why it never worked as a state
machine:

- Nothing reads the difference between `:request` and `:stream`. Every read is
  `:closed` or not-`:closed`; the only site naming both is the `close/1` guard
  `status in [:stream, :request]`, which means "not closed".
- `set_streaming/1` is dead code: no call site in `lib`, `test` or `guides`.
  `Server.handle_continue/2` does not call it on `{:stream, state}`, so no
  channel in the system has ever held `:stream`.
- Even wired up it could not be correct. The stream opens in the conn process,
  and `Relay.stream_loop/1` opens it on *any* notification send — a handler
  that calls `send_progress/4` is streaming while its channel copy still says
  `:request`. The struct cannot track response mode, so it should not carry a
  field claiming to.

Response mode stays where it is actually known: `conn.private.gen_mcp_status`
(`:init | :streaming`) in the relay.

Changes: `:request` → `:open` at both construction sites (`from_request/3`,
`for_pid/2`), the `close/1` guard becomes a single non-`:closed` clause, delete
`set_streaming/1`, update `@type status`.

Free to do now — only `v1.0.0` is tagged (the frozen stateful line), so the
stateless `GenMCP.Mux.Channel` has never shipped in this shape. After v2 it is
a breaking type change for anyone matching on it.

### 3. Documentation

- `Channel` moduledoc: the "Streaming and lifecycle" section describes a
  `:request → :stream → :closed` progression that does not happen. Rewrite as
  two separate statements — sends work until the channel is closed;
  `start_stream/1` switches the response to a stream. Note that `close/1` ends
  the whole response whether or not stream mode was started.
- `start_stream/1` docstring, cross-referencing `close/1`.
- `GenMCP.Suite.Tool` moduledoc: a slow synchronous tool is the case
  `start_stream/1` exists for, distinct from the `{:stream, state}` streaming
  contract already documented there.

## Known trade-off, to document

Blocking in the worker and using a `Task` are not interchangeable, and the
difference is observable:

- **Blocking (`start_stream/1` + slow work inline)**: the worker is inside one
  callback for the whole call, so `{:CHAN_DOWN, ...}` and
  `{:"$gen_mcp", :closed}` sit in its mailbox undequeued. A client
  disconnecting mid-call is not noticed, and `handle_close/3` **never runs at
  all** — the callback returns `{:result, _}`, `Server` stops with
  `{:shutdown, :reply}` (`server.ex:201-203`), and the queued `:CHAN_DOWN` is
  discarded. `terminate_server/1` is only reachable from the `:CHAN_DOWN` /
  `{:"$gen_mcp", :closed}` clauses and there is no `terminate/2`. Verified with
  a throwaway test on 2026-07-29; issue #75 understates this as "runs too
  late".
- **`Task`**: the worker stays idle awaiting the task reply, so it processes the
  disconnect immediately and stops, and a linked task dies with it — the
  in-flight work is abandoned.

So `Task` is for work expensive enough to want cancelling on disconnect (paid
API calls), and `start_stream/1` is for when the socket just needs to stay open.
`start_stream/1` must not be documented as the default without this caveat.

Also worth one sentence where relevant: opening the stream changes the response
from `application/json` to `text/event-stream`. Neither transport reads the
`Accept` header, so the server decides unilaterally. Spec-compliant clients take
both, but tests asserting the direct JSON response shape of a tool will need
updating when it adopts `start_stream/1`.

## Tests

- `start_stream/1` on an open channel delivers `{:"$gen_mcp", :stream}` to
  `channel.client` and returns `:ok`; on a closed channel returns
  `{:error, :closed}` and sends nothing.
- Integration: a tool that calls `start_stream/1`, blocks, then returns
  `{:result, _}` answers over `text/event-stream` with the result as an SSE
  event and a `:keepalive` chunk in between. Needs the 25s
  `@stream_keepalive_timeout` shortened for the test.
- `start_stream/1` then `send_progress/4` produces one stream, not two.
- Repeat `start_stream/1` calls are harmless (asserts the relay's
  `init_stream/1` idempotence end to end).
- Status collapse: every send function rejects `:closed` and accepts `:open`;
  `close/1` works from `:open`.

## Landed 2026-07-30

All three parts are in, `mix libdev.check` green (448 tests, credo, dialyzer,
docs).

- `Channel.start_stream/1`, status collapsed to `:open | :closed`,
  `set_streaming/1` deleted.
- Docs: `Channel` moduledoc split into "Lifecycle" and "Streaming",
  `start_stream/1` docstring, a "Slow tools" section in the
  `GenMCP.Suite.Tool` moduledoc, and pointers from `c:GenMCP.Suite.Tool.call/3`
  and `c:GenMCP.handle_request/3`.
- Tests: `channel_test.exs` (`describe "start_stream/1"`, `describe "status"`)
  and `streamable_http_test.exs` (`describe "Channel.start_stream/1"`, four
  end-to-end cases including keepalives arriving while the handler blocks).

One addition beyond the planned scope, needed to test keepalives at all: the
relay's keepalive interval is now read per timer start from
`Application.get_env(:gen_mcp, :stream_keepalive_timeout)`, defaulting to the
same 25s attribute. It is an internal knob on a `@moduledoc false` module, set
and restored by the test helper `short_keepalive/1`. Nothing else in the tree had
ever asserted that a keepalive is emitted.

Also observed, not changed: a keepalive is chunked as the bare comment line
`":keepalive\n"`, with no blank line after it. Clients treat it as an SSE comment
and ignore it, so it does its job, but it fuses with the next event when a naive
parser splits on `"\n\n"` (see `sse_payloads/1` in `streamable_http_test.exs`,
and the `Enum.reject(&(&1 == ":keepalive"))` in `v2511_compat_test.exs` which
only works when a keepalive is the last thing in the buffer).

## Guide, both halves of #74

Scope decision 2026-07-30: the v2 upgrade guide corrections are done here rather
than by reopening spec 014, because the reasoning behind them is the reasoning
for `start_stream/1` above.

### `Porting async tools`, restructured

The section was titled "Most async tools become synchronous" and recommended
running the work inline, which is the port that silently drops the keepalives. A
v1 `{:async, ...}` tool answered over SSE, so the guide's own recommendation
changed observable behaviour while framing the wire change as a test-fixture
problem. Now three shapes, in the order to try them:

1. **Work that finishes quickly** (`sync_port`, unchanged) plus the wire note:
   this is the one shape that moves the response to `application/json`, so it is
   the one whose SSE assertions need rewriting.
2. **Work that takes a while** (`slow_port`, new): `start_stream/1` then inline
   work. Preceded by a `{: .warning}` admonition on the silent keepalive loss,
   matching the two admonitions the guide already uses for changes that compile
   and pass tests but break against real clients.
3. **Work driven by messages from elsewhere** (`stream_port`, rewritten):
   subscribe to a `Phoenix.PubSub` topic in `call/3`, return `{:stream, state}`,
   translate in `handle_message/4`.

Shape 3 was a `Task.Supervisor.async_nolink/2` example with two traps about
linking and the raw `{ref, value}` message. Replaced on the user's call: a dev
holding a `Task` is an advanced case with its own specifics, and the guide adds
little there, while the event-source shape is what the return tuple is for. The
"raw process message" point survives as one clause of the surrounding prose,
where it holds for any source.

The disconnect trade-off is stated where it is actionable, as the thing that
picks shape 3 over shape 2: idle in `handle_message/4` means the disconnect is
seen immediately and `handle_close/3` can cancel the job, blocking inline means
it is seen when the work returns.

### `:allowed_origins`

New subsection under "Swap the transport on the existing route", the other half
of #74. Verified against both transports before writing: the option is on
`GenMCP.Transport.StreamableHTTP` and `.V2511` alike, `default: []`, type
`{:or, [{:in, [:any]}, {:list, :string}]}`, a non-allowlisted `Origin` gets 403,
and a request with no `Origin` is always accepted. That last part gets its own
`{: .warning}`: it is why an upgraded app looks healthy in CI and fails only for
browser clients after deploy.

`guides/001.getting-started.md` is left alone. A keepalive caveat does not belong
in a first-tool walkthrough, and `GenMCP.Suite.Tool` now carries it.
