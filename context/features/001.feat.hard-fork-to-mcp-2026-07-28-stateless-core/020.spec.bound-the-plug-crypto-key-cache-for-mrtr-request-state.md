# Bound the Plug.Crypto key cache for MRTR request state

Every MRTR round trip leaks a permanent ETS entry. This is in shipped code
(spec 007), found while researching feature 019 and confirmed empirically.

## What happens

`Plug.Crypto.get_secret/3` caches derived keys in `Plug.Crypto.Keys` by default
(`deps/plug_crypto/lib/plug/crypto.ex:361`) — a named public ETS table owned by
the `plug_crypto` application, keyed on
`{secret, salt, iterations, length, digest}` with **no eviction**
(`key_generator.ex:60-70`). `KeyGenerator`'s own documentation warns to use the
ETS cache only when "the secret and salt is a bound set of values".

`GenMCP.Token`'s salts are not all bounded:

* `{:cursor, method}` -> `"gen_mcp cursor " <> method` — bounded by the method
  surface.
* `{:session, ns}` -> `"gen_mcp session v2511"` — a constant.
* `{:reqstate, unicity}` -> `"gen_mcp reqstate " <> sha256(unicity)`
  (`lib/gen_mcp/token.ex:188-195`), where `unicity` is
  `%{tool: tool, params: req.params.arguments}` (`lib/gen_mcp/suite.ex:556-567`)
  — **one distinct salt per distinct set of tool-call arguments**.

So a server whose tools take free-form arguments accumulates one PBKDF2 entry
per distinct call, retained for the life of the VM. It is not a fast leak, but
it is unbounded and grows with exactly the thing an MCP server does most.

Measured (200 distinct request-state purposes vs 200 cursors on one method):

    before=0
    after 200 distinct reqstate purposes=200
    after 200 cursors (same method)=1
    ets memory bytes=64424

About 320 bytes per distinct MRTR call. The cursor figure is the control: a
bounded salt adds one entry no matter how many tokens are minted.

## The fix: a single reqstate salt, binding sealed in the payload

A first iteration passed `cache: nil` for `{:reqstate, _}` only — measurement
showed the cache is pure overhead there (every salt is fresh, so every lookup
misses at the same ~0.22ms) while being a 28x win for the bounded purposes:

| purpose                          | cache on   | cache off |
| -------------------------------- | ---------- | --------- |
| cursor (salt = method name)      | 0.008 ms   | 0.228 ms  |
| reqstate (salt = hash of a call) | 0.220 ms   | 0.220 ms  |

The shipped design goes further and removes the unbounded salt itself. All
request states share the fixed salt `"gen_mcp reqstate"`; the per-call binding
moves inside the token. `encrypt/4` seals `{sha256(unicity), term}` and
`decrypt/4` rehashes the purpose it is given and compares. The envelope is
authenticated (XChaCha20-Poly1305, fresh random nonce per message), so the
embedded hash is as unforgeable as the token itself, and a blob replayed
against a different call fails the comparison exactly as it used to fail
decryption. Same behaviour at the API (`{:error, :invalid}`), same
deterministic-hash property for retries on other nodes.

This is better than the cache opt-out on every axis: request states now *use*
the cache (0.22ms -> 0.008ms per operation), the ETS table is bounded for all
purposes by construction, and there is no cache special case to document.

### The binding hash must cover a canonical encoding

`hash_qualifier/1` passes `:deterministic` to `:erlang.term_to_binary/2`, and
that flag is load-bearing for a reason the original test did not capture.

Insertion order is **not** the risk. A map of at most 32 keys is a flatmap
holding its keys sorted, and above that a HAMT laying them out by key hash, so
building the same map in a different order is byte-stable at any size —
measured identical at 2, 32, 33, 64 and 500 keys, with and without the flag.
The test that claimed to cover this could never have failed.

The real risk is the **atom table**. A small map orders its atom keys by their
table index, assigned as atoms are created, and OTP 26 made that order vary
between VM invocations. Our unicity map is `%{tool: ..., args: ...}` — atom
keys in a small map, exactly the affected shape. Two invocations of one map:

    plain          2D4D0816...  vs  DF5EEB67...   <- differ
    deterministic  B25FC679...  vs  B25FC679...   <- match

So without the flag an MRTR blob minted on one node is `:invalid` on another,
and a single node breaks its own in-flight retries across a restart. This is
the cross-node property the stateless core depends on, and it fails silently.

A single VM cannot re-run with a different atom table, so the test pins the
equivalent invariant: build a map whose atoms were created against term order
(so the two encodings genuinely differ), mint a token past `encrypt/4` carrying
the *canonical* hash, and require `decrypt/4` to accept it. Verified to fail —
and to be the only failure — when the flag is removed.

### The binding hash must stay cryptographic

Considered and rejected: a fast non-crypto hash (`:erlang.phash2/2`) for the
sealed binding, on the theory that encryption protects it. The envelope's
Poly1305 tag (the MAC — no separate HMAC is needed) authenticates the
*embedded copy*, but the comparison is between fingerprints of arguments the
client chooses on **both** sides: it picks the mint-time call and the retry
call, so it can search offline for any colliding *pair* of calls — a birthday
attack against a public function, 2^(n/2) work. SHA-256 puts that at 2^128;
a 32-bit hash collides within ~2^16 tries even before its structure is
exploited. And size is only half the argument: a crypto hash guarantees brute
force is the best attack, where a table-hash like phash2 can be steered
analytically regardless of width. SHA-256 over a unicity map is single-digit
microseconds, noise next to the encryption around it, so the fast hash saves
nothing measurable and gives up the property the blob exists to provide.

## Acceptance — done

* 50 request-state tokens with distinct arguments round-trip while adding zero
  rows to a primed `Plug.Crypto.Keys` table.
* 50 cursor tokens across two methods add exactly two rows, pinning that the
  bounded purposes still cache.
* The binding tests (blob minted for tool A / args X rejected under tool B or
  args Y) now exercise the comparison path — verified to fail when the
  comparison is disabled, so they pin the new mechanism, not the old salt one.
* Both cache tests assert on the delta, not the absolute size — the table is
  global and other tests mint tokens.
* Tokens minted before this change fail to read back (different salt), which
  surfaces as the ordinary `:invalid` request state; blobs live 20 minutes, so
  nothing survives a deploy.
