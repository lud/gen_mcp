# Compile-time validated mcp router macro

Idea, not planned work. An `mcp/2` router macro that validates its options
where they are written, so a misconfigured mount fails the build instead of
every request.

## Why config cannot do this

`config :phoenix, :plug_init_mode, :compile` — the production default — does
not apply to forwarded plugs. It is passed to `Plug.Builder.compile/3`, which
governs pipelines (`deps/phoenix/lib/phoenix/router.ex:959`), the endpoint
(`endpoint.ex:480`) and controller pipelines (`pipeline.ex:82`). A `forward`
takes a different path: `Phoenix.Router.Route.call/2`
(`deps/phoenix/lib/phoenix/router/route.ex:55`) does

    conn = plug.call(conn, plug.init(opts))

unconditionally, per request. `init_mode` is never consulted.

Measured with `plug_init_mode` set to `:compile` and a wrapper plug counting
its own `init/1` calls:

    init calls after the router compiled:    0
    init calls after 3 requests:             3

So a mount missing `:server_name` cannot fail at compile time today, no matter
how the app is configured, and the transport's own `init/1` work is repeated on
every request in production rather than done once.

## The idea

A macro used in place of `forward`, expanding to it:

    import GenMCP.Router

    scope "/mcp" do
      mcp "/", server_name: "My App", server_version: "1.0.0", tools: [MyApp.AddTool]
    end

At expansion the options are literals in the common case, so the macro can run
the same `NimbleOptions` schemas the transport and the Suite use and raise a
`CompileError` pointing at the offending line. It expands to an ordinary
`forward` afterwards, so routing, `defplug/1` and everything else is unchanged.

Open points:

- Non-literal options (a module attribute, a function call) cannot be validated
  at expansion. The macro should detect that and fall back silently to plain
  `forward` rather than pretend.
- Which schema to validate against depends on `:server` — the Suite's options
  apply only when the default server is used. Resolvable at expansion when
  `:server` is literal or absent.
- Whether it should cover the 2025 compat transport too (same problem, same
  fix) or stay 2026-only.
- Naming: `mcp/2` reads well in a `scope` block; `mcp_forward/2` is more
  explicit about what it expands to.

## Relationship to spec 022

Spec 022 makes the *runtime* failure legible — a misconfigured mount currently
answers a bare `500 Internal Error` with the real reason swallowed. That is the
cheap fix and stands on its own. This feature would remove the failure from
runtime entirely, and is only worth building if the DX still bites once errors
are legible.
