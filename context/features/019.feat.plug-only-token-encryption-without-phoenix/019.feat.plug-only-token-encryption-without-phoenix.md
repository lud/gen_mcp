# Plug-only token encryption without Phoenix

**Parked 2026-07-25, as an idea rather than planned work.** Depending on
Phoenix is still useful: an endpoint plus a router does a lot of work for the
user, and it is a lightweight framework to ask for. The research below stands
if that judgement changes — nothing in it expires — but the dependency is a
deliberate choice, not an oversight to be corrected.

The one part worth doing independently of this decision is declaring `{:plug,
"~> 1.14"}` explicitly, since `lib/` uses `Plug.Router` and `Plug.Conn` while
relying on Phoenix to pull them in.

`gen_mcp` advertises itself as mountable in "a Plug or Phoenix router"
(`lib/gen_mcp/transport/streamable_http.ex:35`), but a plain-Plug deployment
cannot use pagination cursors, MRTR request state, or 2025 compatibility
sessions: all three go through `GenMCP.Token`, which requires a Phoenix
endpoint.

Research done 2026-07-25 against `deps/`, with the load-bearing claims verified
against the source and empirically.

## The two symptoms

1. `GenMCP.Mux.Channel.from_request/3` (`lib/gen_mcp/mux/channel.ex:117`) sets
   `:endpoint` only from `conn.private.phoenix_endpoint`. Outside Phoenix it is
   `nil` and `GenMCP.Token` raises `ArgumentError`.
2. `Phoenix.Token` resolves a `Plug.Conn` key source through
   `Phoenix.Controller.endpoint_module/1`, which reads the same private key, so
   passing a plain conn raises `KeyError`. This is what
   `GenMCP.SessionController.Token` hits
   (`lib/gen_mcp/session_controller.ex:173,180`), since it passes the conn.

## What Phoenix actually contributes: nothing

`Phoenix.Token.encrypt/4` and `decrypt/4` are one pipe each — `get_key_base()`
then `Plug.Crypto.encrypt/decrypt` (`deps/phoenix/lib/phoenix/token.ex:159-163`
and `:244-248`, confirmed by reading the source). `get_key_base/1`
(`:252-274`) is a four-clause private resolver, and one of its clauses is
symptom 2.

Everything the `GenMCP.Token` moduledoc credits to Phoenix is `Plug.Crypto`:
PBKDF2-HMAC-SHA256 key derivation (1000 iterations, 32 bytes), the `max_age`
embedded in the plaintext, XChaCha20-Poly1305, the `"XCP."` token prefix, and
`{:error, :missing}` on a nil token.

**The wire format is identical**, verified both directions: a token minted by
`Phoenix.Token` decrypts with `Plug.Crypto` and vice versa. There is no Phoenix
envelope.

## Where the key comes from instead

Phoenix sets `conn.secret_key_base` and `conn.private.phoenix_endpoint` on
adjacent lines of the endpoint's own `call/2`
(`deps/phoenix/lib/phoenix/endpoint.ex:662-663`), both from
`config(:secret_key_base)`. So for every Phoenix request the two sources hold
the same value, and reading `conn.secret_key_base` is strictly more general
than today's endpoint lookup: it covers every current Phoenix user unchanged,
plus any Plug user who sets the field.

Outside Phoenix nothing populates it automatically — adapters do not, and
`Plug.Test.conn/2` leaves it `nil` — so it needs a fallback. Proposed
resolution order, all available where the channel is built
(`make_channel/3` has both `conn` and `conf`):

    explicit :secret_key_base plug option
      -> conn.secret_key_base
      -> conn.private.phoenix_endpoint.config(:secret_key_base)
      -> ArgumentError naming the fix

The explicit option is the escape hatch, not the default. Note that in a
Phoenix `forward` plug options are evaluated at compile time, so a literal
secret would be baked into the router beam — the option should also accept an
MFA or a 0-arity function resolved per request.

## Dependency consequences

`mix.exs:47` declares `{:phoenix, ">= 1.7.0"}` as a hard runtime dependency,
and the only Phoenix code in `lib/` is `token.ex:128` and `token.ex:177`.
Everything else naming Phoenix is documentation prose (`Phoenix.PubSub`
examples). Dropping those two calls makes `phoenix` — and with it
`phoenix_pubsub`, `phoenix_template`, `websock_adapter` — removable from the
runtime, moving to `only: [:dev, :test]` for the test endpoint.

Separately: **`plug` is used but never declared**. `streamable_http.ex:152`
does `use Plug.Router` and `Plug.Conn` is used throughout, relying on Phoenix
to pull Plug in. `{:plug, "~> 1.14"}` and `{:plug_crypto, "~> 2.0"}` need
declaring regardless of whether the rest of this feature happens.

## Compatibility

No migration concern. The format is identical, and for a Phoenix app the key
*value* is identical too, so previously issued tokens keep decrypting. Even if
they did not, cursors and request state live 20 minutes and sessions one day —
nothing survives a deploy. Keeping the `is_atom` endpoint clause preserves
anyone passing an endpoint module to `GenMCP.Token` directly.

## Scope notes

The blast radius is `GenMCP.Token` (two call sites plus its docs), the
`:endpoint` field on `GenMCP.Mux.Channel`, the option schemas and
`make_channel/3` of both transports, and `mix.exs`. The value is demonstrated
by a test mounting the transport in a plain Plug router with no Phoenix in the
pipeline and exercising cursors, MRTR and 2025 sessions.

Not included: the unbounded `Plug.Crypto` key cache, which is a separate
already-shipped defect — see spec 020.

## Note (2026-07-28): who `GenMCP.Token` is for, and an `{:app, qualifier}` purpose

Added while discussing the 2026-07-28 GA announcement, which tells server
authors that if they need state across calls they should "mint an explicit
handle from a tool and have the model pass it back as an argument". That
guidance is **not** a library concern and nothing here implements it: the state
lives in the application's own storage, the handle is a row id, and the lookup
is scoped by whatever the application already authenticated. A UUID beats a
sealed blob for that job — shorter for the model to reproduce, revocable with a
`DELETE`, authorized with a `WHERE`. What the discussion did surface is a
scoping question about `GenMCP.Token` itself, which belongs here because this
feature is what makes the module reachable outside Phoenix.

### 1. Scope the module by purpose in its docs

`GenMCP.Token` seals *protocol* values that must survive a round trip through
an untrusted client and come back intact: pagination cursors, MRTR request
state, 2025 compatibility session ids. For ordinary application work — a
short-lived signed token, a password reset link, anything the application mints
for its own reasons — `Phoenix.Token` and `Plug.Crypto` are the tools to reach
for, and the docs should name both. `Phoenix.Token` is available to every user
today (`mix.exs:47` makes it a hard runtime dependency); `Plug.Crypto` covers
the plain-Plug case this feature enables, and is already in the tree via `plug`
(`mix.lock:38`) though a user would declare it themselves. Since the wire
format is identical in every direction (verified above), neither choice locks
anyone in.

State this by scope, not by prohibition — describe what the module is for and
name the alternatives, rather than warning users off. See the
`avoid-negative-documentation` skill.

### 2. Add an `{:app, qualifier}` purpose

The purpose union is closed today (`{:cursor, String.t()} | {:reqstate, map} |
{:session, String.t()}`), all three library-owned. An application that does want
to seal a term of its own has to squat on `{:cursor, …}`, sharing a salt
namespace with our pagination cursors. An `{:app, qualifier}` purpose closes
that.

The qualifier should carry data, not just a name — `{user_id,
:admin}` as readily as `"cart"`. That is what makes the purpose worth having
over a bare `Plug.Crypto` call, and it works exactly like `{:reqstate, map}`
already does: **the qualifier is never stored in the token**. It is hashed at
mint time, the hash is sealed alongside the value, and `decrypt/4` rehashes the
qualifier it is *given* and compares. The caller has to already know the
invariant to open the token.

That is the concept to document, because it is not what people expect from a
signed token: this validates a value against an invariant **external to the
value**. A token minted under `{:app, {42, :admin}}` opens only for a caller
that can reproduce `{42, :admin}` — so a request arriving as user 43, or as
user 42 who has since lost the admin role, fails to decrypt even though the
sealed payload is untouched and unexpired. The authorization check is the
decryption, not a branch after it. For the traditional shape — mint a token,
open it, then decide what to do — `Phoenix.Token` and `Plug.Crypto` are the
better fit and the docs should say so.

Implementation is the `{:reqstate, map}` mechanism with a new label: a constant
salt (`"gen_mcp app"`), qualifier hashed and sealed inside via the existing
`seal_value/2` and `unseal_value/2` clauses (`token.ex:208-227`). Keeping the
qualifier out of the salt is what makes arbitrary cardinality safe — an
application-supplied string in the salt would reintroduce the unbounded
`Plug.Crypto` key cache that spec 020 fixed. Roughly six lines plus tests, and
`t:purpose/0` widens to accept `{:app, term}`.

### 3. Why it waits for this feature

Accepting application purposes before the key source is fixed would be a door
into a room nobody can enter. `Channel.from_request/3` sets `:endpoint` only
from `conn.private.phoenix_endpoint` (`channel.ex:114-119`), so outside Phoenix
the channel carries `nil` and `endpoint!/1` raises — symptom 1 above. A
plain-Plug user's only route is passing a raw `secret_key_base` binary, and at
that point `Plug.Crypto.encrypt/3` is just as direct. The purpose becomes
worth having at the moment the key source resolution in this feature lands.
