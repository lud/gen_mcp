# Extension methods in the validator

## Goal

Let requests for MCP extension methods, starting with `skills/list` and
`skills/get` from feature 033, pass validation and reach the server as typed
structs, the same way core methods do.

## Context

`GenMCP.Validator` builds its JSON Schema root once at compile time from a
fixed list of `GenMCP.MCP.V2607` request modules (`lib/gen_mcp/validator.ex`).
It maps each method to a JSV key, and any other method answers
`{:error, {:unknown_method, method}}` before the body is read. The transport
calls it first (`lib/gen_mcp/transport/streamable_http.ex:320`), so an
extension method never reaches `GenMCP.Suite`.

The entity modules are generated from the upstream schema pinned in `mix.exs`
(`@schemas_ref "2026-07-28"`). The ext-skills repository publishes no JSON
Schema and no tags. Its types exist only as TypeScript inside
`specification/beta/skills.mdx`. So the extension's JSON Schema has to be
written by hand.

## Design

### Hand-written JSON Schema, generated modules

A JSON Schema file for the extension is written by hand, transcribed from the
TypeScript in the extension spec, and kept in `tools/schemas/ext-skills.json`,
outside the fetched upstream schema directory and outside the hex package. The
schema generator (`tools/gen-rpc-schemas.exs`) takes it through its
`:extension_schemas` option and merges its definitions with the upstream base
schema, so the skills modules are generated like every other entity: same JSV
style, same `MCP:` titles, same encoder derivation, same `mod_config` entries,
and an entry in `ModMap`. `just gen-entities` regenerates them. The file is
replaced by the upstream one if ext-skills ever publishes a schema.

All definitions share one namespace: the generated modules are
`GenMCP.MCP.V2607.ListSkillsRequest`, `GenMCP.MCP.V2607.Skill` and so on, in
`entities.ex`. The generator raises when a name is defined in more than one
source, so a future base definition cannot silently shadow an extension one.
Each module's `@moduledoc` links to the source it was generated from, the
upstream schema or the extension specification. The property descriptions
shared with base results (`cacheScope`, `ttlMs`, `resultType`, `nextCursor`)
are copied from the base schema.

Definitions in the file:

- `ListSkillsRequest`: a paginated request, with `params` referring to the
  base `PaginatedRequestParams`.
- `ListSkillsResult`: `skills`, `nextCursor`, `resultType`, `ttlMs`,
  `cacheScope`, `_meta`.
- `GetSkillRequest` and `GetSkillRequestParams`: `uri` and `_meta`, both
  required, as on `ReadResourceRequestParams`.
- `GetSkillResult`: `skill`, `resultType`, `ttlMs`, `cacheScope`, `_meta`, no
  cursor.
- `Skill`: `uri`; `frontmatter`; `resources`, either an array of
  `SkillResource` or the string `"dynamic"`; optional `_meta`.
- `SkillResource`: `uri`, `digest` (`sha256:` followed by 64 lowercase hex
  digits), `size` (a non-negative integer).

`frontmatter` is an open object requiring `name` and `description`. It must
generate as a plain map, not as a struct module: a struct would lose the keys
it doesn't declare and the encoder would drop its nil values, and hosts
compare frontmatter field by field.

Request metadata and pagination params are `$ref`s to the base `2026-07-28`
definitions. Result modules carry `_meta` like every base result, which the
Suite needs to stamp the server info.

### Registration

The generated skills request modules are in `ModMap`, so the validator
resolves them like core requests. They are added to its `validable` request
list. Kinds and dispatch are unchanged. The set is static and fixed by
gen_mcp: an extension method is recognized because gen_mcp ships support for
it.

### Transport

- `Mcp-Name` validation stays limited to `tools/call`, `prompts/get` and
  `resources/read`. The extension defines no header for its methods.
- `GenMCP.Suite.dispatch_request/3` already answers
  `{:unsupported_method, _}` for validated requests it has no clause for. Until
  spec 036 lands, the skills methods answer "method not found" instead of
  crashing.

## Out of scope

- Extension methods registered by users.
- `resources/directory/read`.
- The 2025 compat transport.

## Acceptance criteria

- [x] `just gen-entities` regenerates the skills modules from the local schema
      file together with the base entities.
- [x] A valid `skills/list` request validates to its struct. So does a
      `skills/get` request with `params.uri`. Both carry the required
      `params._meta`.
- [x] A `skills/get` request without `uri` fails with `{:invalid_body, _}`.
- [x] Skills results encode to the wire shape shown in the extension spec. That
      includes `resources: "dynamic"`, and frontmatter keys passed through
      unchanged, including nested maps.
- [x] With no Suite support yet, a `skills/list` request over HTTP answers
      JSON-RPC `-32601`, not a crash.
