# Skill repositories in the Suite

Product framing is in feature 033. This spec covers how `GenMCP.Suite` serves
skills and the helpers that build skill entries.

## Design

### `GenMCP.Suite.SkillRepo` behaviour

A skill repository is a resource repository that also answers the skills
methods. `ResourceRepo` gains no callback. The skills side is a separate
behaviour:

- `list_skills(cursor, channel, arg)` returns `{[skill], next_cursor}`, where
  each `skill` is a `%GenMCP.MCP.V2607.Skill{}`. It pages over skills, never
  over files. Each entry carries its complete manifest and is never split
  across pages. Its pagination contract is the one `ResourceRepo.list/3` has.
  The name is distinct only because one module implements both behaviours.
- `get_skill(uri, channel, arg)` returns `{:ok, skill}` for a `SKILL.md` URI,
  or `{:error, :not_found}`. It must answer for skills `list_skills/3` doesn't
  list, so it has no default implementation derived from the listing.

A module given in `:skills` must also implement `ResourceRepo` (`prefix/1`,
`read/3`, `list/3`). `use GenMCP.Suite.SkillRepo` declares both `@behaviour`s,
so the compiler reports a missing callback. The Suite expands a skill
repository exactly as a resource repository, with no check at runtime.

The repository's prefix is a namespace. Each skill's root directory, which is
its `SKILL.md` URI minus `/SKILL.md`, is a sub-prefix that the repository
resolves internally. `get_skill/3` goes from a URI to a root with
`Path.dirname/1`. The Suite routes only on the repository prefix and never
knows about individual skills.

### Suite configuration

- A new `:skills` option on `GenMCP.Suite`, carried by `SelfExtension` like
  `:tools`, `:resources` and `:prompts`.
- An optional `skills/2` callback on `GenMCP.Suite.Extension`. It defaults to
  none, so existing extensions keep compiling. `Extension.skills/2` returns `[]`
  when the module doesn't export it.

### Routing

Each request streams repositories per request, as today. Nothing is registered
at startup.

| Request                                         | Repositories streamed, in order                   |
| ----------------------------------------------- | ------------------------------------------------- |
| `resources/list`, `resources/templates/list`    | `Extension.resources/2`                           |
| `resources/read`                                | `Extension.skills/2`, then `Extension.resources/2` |
| `skills/list`                                   | `Extension.skills/2`                              |
| `skills/get`                                    | `Extension.skills/2`                              |

- A repository given only in `:skills` is readable but not listed. Not being
  listed simply means not being in `:resources`: there is no mode flag.
- A repository given in both options is listed through `:resources`.
  `resources/read` may visit it twice. That's harmless, because `find_repo`
  stops at the first prefix match, and a second visit that doesn't match costs
  one `prefix/1` call. There is no deduplication.
- Skill repositories come first in `resources/read`, so the bytes served for a
  skill URI are the ones its manifest describes. This is the general rule for
  repositories that an extension contributes to `resources/read`: plain
  resource repositories are always read last, so an extension can override an
  existing resource, and a plain resource cannot override an extension's.
- `skills/list` paginates over skill repositories with `paginate_repos`.
  Cursors are encoded and signed like the other list cursors.
- `skills/get` runs `find_repo` by prefix over skill repositories, then
  `get_skill/3`. When no repository matches, or the repository answers not
  found, the reply is `-32602`, through the `{:skill_not_found, uri}` error
  tuple in `GenMCP.Error`.
- Prefix routing is unchanged: the first repository whose prefix matches
  answers, and its not-found is final. Prefixes must not overlap, between skill
  repositories as well as between skill and resource repositories.
- With no skill repository configured the extension is not declared. A client
  that calls anyway gets an empty `skills/list` result and `-32602` from
  `skills/get`. There is no special case.
- The `ttlMs` and `cacheScope` on skills results come from the repository's
  `cache_control/1`, as for resources.
- The results are built with `GenMCP.MCP.V2607.list_skills_result/3` and
  `get_skill_result/1`, shaped like the other list and read builders.
  `get_skill_result/1` takes the entry flat (`:uri`, `:frontmatter`,
  `:resources`) or ready-made as `:skill`. `skill/1` builds one entry from the
  same flat options, where `:resources` is a list of `%{uri:, digest:, size:}`
  or `:dynamic`.

### Capabilities

- `resources` is declared when any extension returns resource repositories
  **or** skill repositories. The spec requires `resources` alongside the
  extension.
- `extensions["io.modelcontextprotocol/skills"]` is declared as `%{}` when any
  extension returns skill repositories.

### Overlapping prefixes

- Prefixes must not overlap. Routing stays first-match by prefix, with a final
  not-found: there is no fallback to the next repository and no
  longest-prefix competition. The docs tell users to make every prefix a
  sequence of full path segments ending with a slash, so `skill://foo/` doesn't
  cover `skill://foobar/...`. This applies to resource, prompt and skill
  repositories alike.
- Both listings can advertise an entry that is shadowed on read. This is the
  consequence of an overlap, and the docs say so.
- A skill repository whose prefix covers a resource repository's prefix (for
  example `skill://`) hides that repository from `resources/read` for those
  URIs, while `resources/list` still lists them.
- Two skill repositories with overlapping prefixes are both listed by
  `skills/list`, but only the first answers `skills/get` and `resources/read`.
- A repository given only in `:skills` doesn't appear in `resources/list`.
  Adding it to `:resources` lists files only if its `list/3` is overridden.

### Skill entry helper

`GenMCP.MCP.V2607.skill_entry_from_path(path_to_skill_md, base_uri, opts)`
builds an entry from a path on disk. It:

- takes the skill root on disk as the directory containing `SKILL.md`;
- builds the skill's root URI as `base_uri` followed by the frontmatter
  `name`, URI-encoded as a path segment, inserting a `/` when `base_uri`
  doesn't end with one. The directory name on disk plays no part: clients never see it. The
  extension requires the last URI segment before `/SKILL.md` to equal
  `frontmatter.name`, and deriving the URI from the name satisfies that by
  construction;
- walks it recursively. Everything under the root belongs to this skill,
  including a `SKILL.md` found deeper, which is an ordinary supporting file.
  Symlinks to files are followed, symlinks to directories are not;
- keeps only the files matching the `:extensions` option, a list such as
  `[".md", ".txt", ".js"]`. It defaults to every file. `SKILL.md` is always
  kept;
- gives each file the URI `<skill root URI>/<relative path>`, each path
  segment URI-encoded so that characters like `#` or `?` stay in the path;
- computes `sha256:<hex>` and the byte size of each file, whether its content
  is valid UTF-8, and its MIME type with `MIME.from_path/1`;
- parses the `SKILL.md` frontmatter with `yamerl`, to binaries and maps, so
  `frontmatter` is the verbatim YAML rendered as a plain JSON object: YAML
  `null` becomes `nil`, and non-string keys become strings;
- checks that `name` and `description` are present and are strings;
- returns `{skill, files}`: the `%GenMCP.MCP.V2607.Skill{}` entry, and a map
  from each file's URI to `%{path: relative_path, text?: boolean, mime_type:
  mime_type}`.

Any failure raises: a missing or invalid frontmatter, an unreadable file. The helper is meant for compile time, where that is
a compilation error.

It warns when a skill exceeds 512 files or 16 MiB, the limits hosts are
required to accept.

It also warns when `name` doesn't follow the Agent Skills naming rules, with a
simple regex check: at most 64 characters matching
`^[a-z0-9]+(-[a-z0-9]+)*$` (lowercase letters, digits and single hyphens, no
hyphen at either end). The skill is still served.

`yamerl` is an optional dependency of gen_mcp, used only by this helper. The
helper starts the `:yamerl` application itself and calls it directly. There is
no guard: without the dependency the call fails. `mime` becomes an explicit
dependency of gen_mcp (it was only a transitive one through `plug`).

### Compile-time repository

`use GenMCP.Suite.SkillRepo` only declares the behaviours. Compiling a
directory of skills is a separate module, `GenMCP.Suite.SkillRepo.Static`:

    defmodule MyApp.Skills do
      use GenMCP.Suite.SkillRepo.Static,
        otp_app: :my_app,
        dir: "skills/user-skills",
        prefix: "skill://my-app/"
    end

Options:

- `:otp_app` and `:dir`, both required. `dir` is relative to the application's
  `priv` directory, so the files ship with a release. At compile time the
  macro reads the project's `priv/<dir>`. At runtime `read/3` reads from
  `Application.app_dir(otp_app, ["priv", dir])`. Compilation fails when
  `:otp_app` isn't the application being compiled.
- `:prefix`, required. There is no default. It is the repository prefix, with
  a trailing `/` added when missing, so `skill://acme` cannot cover
  `skill://acme-tools/`.
- `:extensions`, passed to the path helper. Each must start with a dot.
- `:page_size`, the number of skills per `list_skills/3` page. Defaults to 20.

Behaviour:

- The skills are the direct subdirectories of `dir` that contain a `SKILL.md`.
  There is no deeper scan. Everything else inside such a directory, at any
  depth and including another `SKILL.md`, is a companion file of that skill.
  Direct subdirectories without a `SKILL.md`, and files directly in `dir`, are
  ignored.
- A skill's URI is `prefix`, its frontmatter `name`, then `/SKILL.md`. Two
  directories declaring the same `name` would get the same URI, which is a
  compilation error. A deeper
  hierarchy is made of several modules, each with its own `dir` and a longer
  `prefix` such as `skill://my-app/billing/`.
- At compile time, runs the path helper on every skill directory. Only metadata
  stays in the module: entries plus an index from URI to relative path and
  text-or-blob flag. File contents are never embedded. They are read from disk
  on every `read/3`.
- `read/3` returns valid UTF-8 files as `text` and the others as base64
  `blob`, through `read_resource_result/1`, so the bytes a host recovers are
  the ones the digest covers. Each result carries the file's MIME type.
- Declares every file with `@external_resource`, so editing a skill recompiles
  the module. Defines `__mix_recompile__?/0`, which scans `dir` and compares
  the file list with the compiled one, so adding or removing a file recompiles
  too.
- Cache hints follow the resource repository rule: the module's
  `cache_control/1` when it defines one. Otherwise a `cache_control/1`
  returning `GenMCP.MCP.V2607.default_cache_control/0` is generated before
  compilation ends. The same hint goes on
  `skills/list`, `skills/get` and the generated `read/3` results.
- Generates overridable `prefix/1`, `read/3`, `list_skills/3`, `get_skill/3`, and
  `list/3`. `list/3` returns `{[], nil}` by default, so nothing is listed by
  accident.

## Out of scope

- `resources/directory/read`.
- Built-in caching of manifests computed at runtime for dynamic skills.
- A helper building an entry from in-memory files for generated skills. A
  repository serving generated skills computes its digests itself, or answers
  `"dynamic"`.
- Detecting overlapping prefixes.
- Scanning below the first level of `dir`, and selecting skills with a glob
  pattern.

## Acceptance criteria

- [x] `skills/list` returns entries from every skill repository, paginated
      across repositories, with `resultType`, `ttlMs` and `cacheScope`.
- [x] `skills/get` returns the entry for a known `SKILL.md` URI, including a
      skill `list_skills/3` doesn't list, and `-32602` for an unknown one.
- [x] `resources/read` serves skill files. A skill repository wins over an
      overlapping resource repository.
- [x] A repository given only in `:skills` is absent from `resources/list` and
      `resources/templates/list`. It is present in `resources/list` when also in
      `:resources` with an overridden `list/3`.
- [x] `server/discover` declares `resources` and
      `extensions["io.modelcontextprotocol/skills"]` when only `:skills` is
      configured.
- [x] The digests and sizes computed by the helper match the bytes that
      `resources/read` returns: the UTF-8 bytes of `text` for a text file, the
      decoded `blob` for a file that isn't valid UTF-8.
- [x] Only direct subdirectories of `dir` with a `SKILL.md` are skills. A
      `SKILL.md` deeper inside one is listed in that skill's manifest and is
      not a skill of its own. A direct subdirectory without a `SKILL.md` is
      ignored.
- [x] A file excluded by `:extensions` is neither in the manifest nor readable.
- [x] A `SKILL.md` with missing frontmatter fields fails compilation. So do
      two skill directories declaring the same `name`.
- [x] A `name` that breaks the naming rules emits a compilation warning and
      the skill is still served.
- [x] A skill whose directory name differs from its frontmatter `name` is
      served under the `name`.
- [x] The compile-time `list_skills/3` pages by `:page_size`.
- [x] With no skill repository configured, `skills/list` returns an empty list
      and `skills/get` answers `-32602`.
- [x] Editing, adding or removing a file under `dir` recompiles the module.
- [x] An extension without `skills/2` still works.
