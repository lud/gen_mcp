# Skills extension support

## Goal

Let a gen_mcp server publish Agent Skills through the official MCP Skills
extension (`io.modelcontextprotocol/skills`, SEP-2640, Final). The common case
is a directory of skills shipped in the application's `priv`, served with a
couple of lines of configuration. Generated skills and skills stored elsewhere
stay possible.

## Motivation

Resources see little use in the wild, while skills are popular. The extension
is how hosts discover a server's workflow instructions and the files that
support them, and load them on demand. The protocol binding is mostly
bookkeeping: per-file SHA-256 digests and byte sizes, frontmatter passed through
verbatim. Hosts reject any skill whose digests don't match. gen_mcp should do
that bookkeeping so users only write `SKILL.md` files.

Sources:

- Overview: https://modelcontextprotocol.io/extensions/skills/overview
- Specification: https://github.com/modelcontextprotocol/ext-skills, file
  `specification/beta/skills.mdx`. Targets base revision `2026-07-28`.

## What the extension asks of a server

- Declare `capabilities.extensions["io.modelcontextprotocol/skills"]` and the
  `resources` capability in `server/discover`.
- Answer `skills/list` (paginated) and `skills/get` (by `SKILL.md` URI). Both
  return entries made of `uri`, `frontmatter` and `resources`. `resources` is a
  complete manifest of `{uri, digest, size}`, or `"dynamic"`.
- Serve every skill file through the ordinary `resources/read`.
- `skills/get` answers for every skill served, listed or not. An unknown URI
  answers `-32602`.
- `skill://` is the recommended scheme, not a mandatory one. Skill paths may be
  nested (`skill://acme/billing/refunds/SKILL.md`), and only the last segment
  has to match the skill's `name`.

## Product decisions

- **A skill repository is a resource repository.** Skill files are resources,
  so a skill repository joins the existing prefix-routed resource repositories.
  It is not a parallel system. Its prefix is a namespace that can hold many
  skills. Each skill's root directory is a sub-prefix that the repository
  resolves itself, so one repository serves many skills.
- **Skills are served before other resources.** When a skill repository and a
  resource repository both match a URI in `resources/read`, the skill
  repository answers. This guarantees that the bytes `resources/read` serves
  are the ones `skills/get` advertised.
- **Skill files are not listed by default.** A repository given only to the
  Suite's `:skills` option doesn't appear in `resources/list`. Skills have their
  own listing.
- **Static skills are compiled.** A helper builds skill entries from a
  directory at compile time and keeps the metadata in memory, so manifests are
  correct by construction.
- **Overlapping prefixes are the user's responsibility.** Prefixes must not
  overlap, between skill repositories or with resource repositories. This is
  documented, not detected, and the docs recommend prefixes ending with a
  slash.

## Scope

- `skills/list`, `skills/get`, and `resources/read` for skill files, on the
  2026 stateless transport.
- Suite configuration: a `:skills` option and a skills callback on Suite
  extensions.
- A helper that builds a skill entry from a `SKILL.md` path, and a compile-time
  skill repository for a directory of skills.

## Out of scope

- `resources/directory/read` and the `directoryRead` setting. The extension
  declaration is an empty object.
- The 2025 compat transport. The extension targets `2026-07-28` and later.
- Host-side concerns: approval, verification, caching.

## Specs

- 035: extension methods in the validator. This is the prerequisite: today
  `skills/list` is rejected as an unknown method before it reaches the Suite.
- 036: skill repositories in the Suite.
